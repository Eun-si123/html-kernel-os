# HTML Kernel OS — 창립자 인터뷰 결정 기록

> Snapshot: 2026-11-22 (KST), 인터뷰 1~19 완료. 이 문서는 **사용자의 목표·선호를 기록**한 것이며, 새 기능의 구현·검증·배포 완료를 의미하지 않는다.
> 후속 인터뷰나 실제 실험 결과가 기존 결론을 바꿀 수 있다. [결정 레지스터](DECISIONS.md), [현재 구현 상태](STATUS.md), [개발 로드맵](ROADMAP.md)을 함께 읽을 것.

## 인터뷰 1~19: 원답변 기반 기록

| 번호 | 질문 주제 | 사용자가 선택한 답변 및 추가 의견 |
| --- | --- | --- |
| 1 | 장기 목표 | **C — 둘 다.** HTML처럼 생긴 프로그래밍 언어와 독립 OS를 함께 지향. |
| 2 | 기존 HTML과의 관계 | **B — HTML 같은 새 문법 허용.** B 또는 기존 HTML을 최대한 유지하는 **A**를 매우 우선. 정말 불가피하면 혼합 방식 **C**도 가능. |
| 3 | 언어의 적용 범위 | **A — 지금은 커널·OS 개발에 집중.** 이 분야가 충분히 잘 작동한다면 다른 범위(B, C, D)로 확장할 의향. 확장의 판정 기준은 미정. |
| 4 | 다른 분야로 확장할 준비 기준 | **C — 실사용 가능한 독립 OS.** 단, Linux나 Windows를 활용해 HTML로 가동되는 **시제품부터 실사용**할 수 있으면 괜찮다고 명시. '독립 OS'와 초기 시제품은 서로 다른 단계. |
| 5 | HTML의 OS 내 역할 | **C 또는 D 사이에서 미결정.** Discord 대화를 보고 흥미를 느꼈으며, HTML 기반 UI·시스템 구현 및 궁극적인 커널 구현 가능성을 함께 탐색. 확정 선택으로 기록하지 말 것. |
| 6 | 첫 시연 목표 | **D — 모두 가능하게 하되 단계적으로 구현.** |
| 7 | 기술 우선순위 | **D — 사용 편의성, 성능, 실사용 안정성을 균형 있게 발전.** |
| 8 | 초기 플랫폼 전략 | **D — Linux 기반 시제품 + 독립 커널 병행.** |
| 9 | 초기 개발 집중점 | **C — 공통 컴파일러와 언어 완성도 우선.** 상황에 따라 **E — 유연한 우선순위 변경**도 허용. |
| 10 | 언어의 편의성과 제어 | **C — 평소엔 쉽고 필요할 때 저수준 제어.** 추가로 **D — 용도별 모드/규칙**, **E — 사용성·성능·안전성 비교 실험** 선호. |
| 11 | HTML UI와 시스템 태그의 관계 | **D — 실제로 만들어 보고 결정.** 통합/역할 분리/호환성 정책은 확정하지 않음. |
| 12 | 기존 앱 호환 | **E — Windows·Linux 기존 프로그램과의 호환성은 나중에 결정.** 현재 필수 완료 조건으로 강제하지 않음. |
| 13 | 초기 기능 구현 순서 | **E — 쉬운 것부터 검증하며 단계적으로 구현.** |
| 14 | 컴파일 오류 처리 정책 | **E — 실제 사용 경험을 비교해 결정.** 엄격 검증/자동 변환/친절한 진단 방식 중 하나를 아직 확정하지 않음. |
| 15 | 개발 환경 | **D + E — 기존 CLI·에디터 도구를 단계적으로 활용**, 실제 사용자 경험과 개발·유지 비용을 비교해 결정. 전용 IDE는 미확정. |
| 16 | AI 에이전트 개발 자율성 | **D — AI가 개선점 발굴, 설계 변경, 리팩터링, 기능 추가를 적극 주도.** 추가로 **C — 검증된 개발·병합 자율화**, **E — 위험도·작업 규모에 따른 승인 수준 조절**도 선호. 사용자는 프로그래밍 지식이 거의 없으므로 코드 수준 판단을 강요하지 않고 쉬운 설명과 재현 가능한 검증 결과를 제공해야 함. 파괴적/대외 영향이 큰 변경에 대한 무제한 승인으로 해석하지 않음. |
| 17 | 결과 검증·보고 | **C — 사용자가 직접 체험할 수 있는 시제품 우선.** 추가로 **D — 쉬운 요약·실행 증거·시제품 함께 제공**, **E — 작업 중요도에 따라 검증과 보고 수준 조절** 선호. 실제 실행 가능한 산출물이 만들어지기 전에는 미구현이라고 명확히 밝힐 것. |
| 18 | 시제품 실행·배포 | **D — 가상머신부터 실제 PC까지 단계적 확장** 선택. 추가 의견 **'다?' — 모든 실행 선택지에 관심**. **웹 브라우저에서도 실행되는 체험 환경**을 원함. Windows 원클릭 실행, VM 부팅, 웹 체험, 실제 PC USB 부팅은 서로 다른 제공 방식으로 단계적 가능성 검토; 모두 구현 완료라고 주장하지 않음. |
| 19 | 가장 뿌듯할 첫 시연 | **A — HTML에서 만든 코드가 실제 커널로 부팅하는 장면** 선호. 다른 기능도 모두 원하지만, 우선 A만 성공해도 HTML 스타일 문법이 실제 프로그래밍 언어로 컴파일되고 OS·커널 코드를 작성할 수 있다는 것을 증명하는 데 의미를 둠. 추가 희망: **Windows 93 / Windows 96 같은 브라우저 내 OS 체험**. 이러한 웹 경험과 실제 네이티브 커널 부팅은 기술적으로 구별해야 함. |

## 현재 합의된 방향 (목표; 구현 사실과 혼동 금지)

1. **언어 중심:** HTML 같은 태그 문법을 주축으로 하는 네이티브 시스템 언어를 발전시키며, 표준 HTML 자체가 커널을 실행한다는 주장은 하지 않는다.
2. **공통 기반:** 공통 언어/컴파일러를 우선 개발하고, **Linux 활용 시제품**과 **독립 부팅 커널**을 별도의 검증 경로로 병행 탐색한다. 공유 가능한 부분만 공유하며 플랫폼 전용 런타임·API 차이는 인정한다.
3. **실사용을 향한 단계적 확장:** 처음부터 광범위한 게임/앱/하드웨어 지원을 목표로 하지 않는다. 작은 언어 기능, 실제 실행, 재현 가능한 테스트를 통해 확대한다.
4. **개발 기준:** 초보자 친화성, 네이티브 성능 목표, 안전성·안정성의 균형을 추구하되 실제 측정으로 판단한다.
5. **기존 구성요소 재사용:** Linux/C/Rust/기존 툴체인 활용 가능. 기존 Windows를 커널처럼 자유롭게 개조하거나 재배포할 수 있다는 뜻은 아니다.
6. **AI 자율 개발:** 발견→설계→구현→테스트→검토→안전한 병합까지 능동적으로 진행하되, 변경 위험도에 맞춰 제한한다. 사용자가 프로그래밍을 이해한다고 전제하지 말고 목적·검증 증거·남은 위험을 쉬운 언어로 보고한다.
7. **체험 가능한 결과 우선:** 실제로 실행·부팅해 볼 수 있는 시제품을 중요한 완료 산출물로 지향한다. 가능할 때 실행 방법, 검증 로그, 한계와 안전 주의사항을 함께 제공한다. 리스크가 낮은 문서 수정이나 소규모 버그 픽스에 매번 배포 파일을 요구하지는 않는다.
8. **배포·체험 경로:** 가상머신에서 먼저 검증한 뒤 실제 PC로 확장한다. Windows 원클릭 실행과 **브라우저 내 체험**도 원하는 목표다. Windows 93 / Windows 96 같은 웹 체험 방식을 참고하되, 웹 UI 시뮬레이션과 실제 커널 실행을 구분한다. 브라우저에서는 가능한 경우 호환되는 VM 이미지를 브라우저용 x86 에뮬레이터에서 실제 부팅하는 방식을 우선 조사한다. 브라우저용 에뮬레이터와 QEMU의 지원 CPU/부트 프로토콜이 다를 수 있으므로 호환성은 아직 미확인이다.
9. **첫 성공 장면:** 기능이 적어도 HTML 스타일 소스를 컴파일하여 **실제 커널이 부팅하는 것**을 첫 체험 목표로 우선한다. 소스 변경 → 생성 산출물 변경 → 부팅 동작 변경을 검증해 출처를 확인하며, 미구현 기능을 가진 겉모습만의 웹 OS를 부팅 증거로 삼지 않는다.

## 아직 결정되지 않은 것

- UI와 시스템 태그를 하나의 사용 가능 집합으로 둘지, 같은 언어 안에서 권한·실행 환경별로 구분할지 (인터뷰 11).
- HTML 언어로 자체 커널을 얼마나 많이 구현할지, Linux 시제품에서 어떤 컴포넌트를 HTML로 작성할지 (인터뷰 5, 8).
- '완벽히 잘 됨' 또는 '실사용 가능'의 구체적인 측정 기준과 확장 시점 (인터뷰 3, 4).
- 오류 복구·컴파일 진단 정책, 개발 도구/IDE의 최종 형태, 기존 Linux/Windows 앱과의 호환성 (인터뷰 12, 14, 15).
- 컴파일러 백엔드, 실제 벤치마크 수치, 독립 커널 부트·드라이버 지원 범위 등 기술 선택은 별도 설계·검증 필요.
- 브라우저에서 실제 부팅 가능한 x86 이미지 호환 범위, 에뮬레이션 속도·메모리 사용·모바일 호환·배포 라이선스와 사이트 호스팅 활성화는 별도 조사·검증 후 결정. 브라우저 데모를 곧바로 커널 검증 증거로 사용하지 않는다.

## 다음 단계 / 문서 관리

- 인터뷰는 **19번까지 완료**, 20번 최종 질문 예정. 약 20문항을 목표로 하되 상황에 따라 조기 종료 또는 필요한 질문만 추가한다.
- 새 인터뷰 답변은 해당 번호와 **답변의 확정성**을 구분해 이 문서에 반영한다. 가설이나 조언을 사용자 결정으로 둔갑시키지 않는다.
- 이번 기록 작업은 **문서만 수정**한다. 로드맵 M0~M6의 기존 검증 게이트나 STATUS의 현재 능력을 소급 변경하지 않는다.
- 이후 Linux 시제품을 개발 계획에 편입할 때는 별도 마일스톤/검증 경로를 설계해 [ROADMAP.md](ROADMAP.md)에 반영하며, 단순 HTML 데스크톱 데모와 실제 네이티브 실행을 구분한다.

## 배경

프로젝트 출발점은 Discord에서 제안된 HTML 커널 아이디어(예: `<kernel boot="true">`)를 재미있게 보고, 농담처럼 보이는 구상을 실제 작동하는 시스템 언어와 OS 실험으로 만들고 싶다는 관심이었다. 해당 태그들은 아이디어일 뿐 표준 HTML이나 현재 구현된 컴파일러 기능이 아니다.
