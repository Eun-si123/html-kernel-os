# HTML Kernel OS — 실행 중심 개발 계획 (2026-11-22)

> 이 문서는 [창립자 인터뷰 1~20](INTERVIEW_DECISIONS.md)을 실행 가능한 검증 단계로 바꾸는 **계획**이다. 실제 구현 증거는 [STATUS](STATUS.md)에 기록한다. 기존 [M0–M6](ROADMAP.md) 마일스톤 ID와 부팅 완료 기준은 유지한다.

## 개발의 목적과 첫 성공

- **첫 성공 S1:** HTML 스타일 소스의 내용을 바꾸어 컴파일했을 때, **실제로 QEMU에서 부팅한 커널의 출력도 바뀜**을 입증한다. 웹사이트에 부팅 화면을 흉내 내는 것으로 대신하지 않는다.
- **다음 성공 S2:** 언어의 타입·제어 흐름과 일부 메모리·입출력 같은 실제 시스템 기능을 HTML로 작성하고 실행한다.
- **더 먼 성공 S3:** 독립 커널에서 HTML 코드의 역할과 실용성을 확대하고, 운영 환경·하드웨어 호환성과 품질을 단계적으로 끌어올린다. 미래의 기준을 높여도 검증된 S1 성공은 취소하지 않는다.
- **D + E 원칙:** S1→S2→S3으로 가되 실제 테스트, 위험, 개발 비용에 따라 순서를 조정한다. 합격 기준을 낮춰서 성공한 척하지 않는다.

## 코드에서 확인한 출발점 — 인터뷰 당시 기준 기록

> **현재 상태 갱신 (2026-11-22):** P1/M1 실제 QEMU BIOS 커널 부팅은 로컬 및 GitHub CI에서 검증 완료. v64 WebAssembly 브라우저 에뮬레이터에서도 공개 Pages의 실제 ISO 부팅과 COM1 출력 수신을 Chromium으로 확인했어. 아래 표는 **개발 전 기준선의 역사적 기록**이며, 최신 상태는 [STATUS.md](STATUS.md)를 우선해.

| 항목 | 현재 확인 | 아직 아닌 것 |
| --- | --- | --- |
| 문법·컴파일러 | `compiler/htmlk.py`: `kernel/onboot/print/halt`의 작은 집합을 C `kernel_main()`으로 변환 | 변수·함수·범용 HTML |
| 빌드 | HTML → C → x86-64 **relocatable ELF object**; GCC가 실제 컴파일 | 부팅 가능한 링크된 이미지 |
| 검사 | 기존 Python source/site 12개 + scripts 18개 테스트, 문서·roadmap 검사 | QEMU 부팅 또는 Linux 실행 검증 |
| QEMU / 실기기 | **NOT RUN** (부팅 가능한 이미지 없음) | 실제 독립 커널 부팅 |

위 검증은 기록 시점의 로컬 검사이며, 매 변경마다 정확한 커밋과 CI에 맞춰 재확인한다.

## 공통 언어, 서로 다른 실행 환경

- 한 언어의 파서/의미 분석/중간 표현을 재사용하고, 필요할 때만 **freestanding kernel / Linux userspace**용 코드를 별도 생성한다.
- 현재 x86 I/O 포트 `0xE9`에 쓰는 코드는 QEMU 개발용이다. **Linux 일반 사용자 프로그램에서는 직접 실행할 수 없다.** Linux 출력은 별도의 런타임/호출 경로를 사용해야 한다.
- 브라우저에서는 실제 부팅 이미지를 호환되는 x86 에뮬레이터로 실행하는 방식과, Windows 93/96처럼 UI만 시연하는 방식이 다르다. 반드시 명확히 구분한다.

## 단계별 구현·완료 기준

### P0. 공통 컴파일러 기반을 신뢰할 수 있게 만들기 (M1과 병행, 단기 1순위)

- 기존 `examples/kernel.html`을 유지하면서 태그·속성·이스케이프·중첩·허용 범위의 최소 문법 계약을 명확히 한다.
- 잘못된 태그, 중복 속성, 잘못 닫힌 요소, 과도한 출력 길이, 비정상 입력과 결과의 결정성을 확인하는 **양성·음성 테스트**를 보강한다.
- 의미 분석과 플랫폼별 입출력 분리는 필요성이 확인된 최소 범위부터 도입한다. 처음부터 LLVM 전체 도입·컴파일러 중복 구현은 하지 않는다.
- **통과:** 기존 M0 샘플과 오브젝트 컴파일 유지 + 새 오류 사례 안정적으로 거부 + 테스트 결과 재현.
- **실패:** 알 수 없는 코드를 조용히 허용하거나, 출력 의미를 깨뜨리거나, 오브젝트 생성만으로 실행 지원을 주장함.

### P1. M1: HTML 코드로 만든 커널의 QEMU 실제 부팅 — **완료·검증됨**

- 담당 이슈: [M1 #3](https://github.com/Eun-si123/html-kernel-os/issues/3) (**완료/닫힘**). 핵심 구현 [PR #13](https://github.com/Eun-si123/html-kernel-os/pull/13), 실제 QEMU 독립 CI `45027891902` PASS, 브라우저 부팅과 Pages 배포 [PR #16](https://github.com/Eun-si123/html-kernel-os/pull/16) 및 run `45029073658` PASS. 아래는 실제 구현에 적용한 검증 기준이야.
- 출처와 라이선스를 확인한 부트로더·부팅 프로토콜(예: Limine 후보)을 정확한 버전으로 고정한다.
- `kernel_main()`을 최소 부트 진입 코드/링커 스크립트와 연결하고, **재현 가능한 부팅 이미지**를 만든다.
- 헤드리스 QEMU에서 debugcon `0xE9` 출력과 제한 시간을 검증한다. 부트로더에 성공 문자열을 하드코딩하지 않는다.
- **출처 검증:** HTML 안의 `<print>` 내용을 바꾼 뒤 새 이미지를 만들면 QEMU 출력도 바뀌어야 한다. 잘못된 출력·시간 초과는 반드시 실패해야 한다.
- **통과:** 정확한 명령/버전/이미지 해시/콘솔 로그/CI 링크가 있는 실제 부팅 PASS와 음성 테스트 PASS.
- **미통과:** C 오브젝트만 생성, 정적 스크린샷, 부팅 로그를 흉내 낸 페이지, QEMU를 실행하지 않은 CI.

### P2. Linux 최소 실행 시제품 (공통 컴파일러 공유의 첫 증거)

- P0의 공통 의미 분석을 활용하되 **일반 사용자 권한** Linux 실행 파일을 만드는 타깃을 작게 추가한다.
- 같은 언어에서 작은 출력 프로그램을 네이티브 컴파일하고, 표준 출력·프로세스 종료 코드·잘못된 소스 실패를 테스트한다.
- 커널 `halt`와 사용자 프로그램 종료의 차이를 문서화한다. Linux 커널 또는 데스크톱 전체를 만들었다고 주장하지 않는다.
- **통과:** 실제 Linux 실행 파일의 출력·종료·오류를 재현 가능한 테스트로 입증.

### P3. 편리한 시스템 언어 확장 (M2 연계)

- 변수·자료형·계산·조건문·반복문·함수·오류 위치·명시적 저수준 기능을 한 번에 다 넣지 않고 검증 가능한 단위로 구현한다.
- 양쪽 환경에 적용 가능한 예제는 Linux와 QEMU에서 모두 시험한다. 권한 API는 무작정 섞지 않는다.
- Python처럼 쓰기 쉬운지 초보자 작업으로 측정하고, C++/Rust 성능 비교는 동등한 실제 코드가 실행되기 시작한 후 한다.
- **통과:** [M2의 기존 게이트](ROADMAP.md) + Linux 측 실제 동작 증거.

### P4. Windows·웹 브라우저 시제품 체험 경로

- **브라우저 부팅은 한 환경에서 검증됨:** 공개 Pages `play.html`에서 v64 x86-64 WebAssembly가 실제 M1 ISO를 부팅하고 COM1 문자열을 수신했다(Chromium/Playwright). QEMU에서 된다고 모든 다른 브라우저·모바일에서도 된다는 보장은 없어.
- 가능하면 Windows에서 실행하기 쉬운 QEMU 래퍼를 검토한다. 실행 파일의 배포·릴리스는 별도 권한과 출처 확인 후 결정한다.
- Windows 93/96 같은 웹 데스크톱은 UX 참고 대상. UI 시뮬레이션은 **UI 시뮬레이션**이라고 표기하고 **실제 부팅 증거**로 사용하지 않는다.
- **통과(부팅 경로):** 브라우저가 실제 부팅 이미지를 실행하고 소스에서 유래한 변경 출력이 확인됨.
- **통과(UI 시연):** 별도 표시된 인터랙티브 웹 데모로서의 동작만 확인됨.
- 기존 개인 `github.io` 보존. 프로젝트 Pages 활성화나 배포·공개 인프라 변경은 별도 승인으로 진행.

### P5. OS 핵심 기능과 실제 하드웨어 (M3–M6)

- **M3:** 메모리 맵/할당·가상 메모리·예외/인터럽트. **M4:** 태스크·스케줄러·권한 분리.
- **M5:** 입력 터미널·작은 읽기 전용 파일시스템·별도 프로그램 실행. **M6:** 지원 기종을 한정한 안전한 실기기 검증.
- 실기기 첫 시험에서 펌웨어를 수정하거나 운영 중 디스크에 자동으로 기록하지 않는다. 복구·롤백 계획 필수.
- 기존 Linux/Windows 프로그램 호환, 광범위한 GPU/게임·드라이버 생태계, 독자 IDE는 **추후 결정**.

**병행 정책:** P0은 P1의 부팅 설계와 함께 진행하되, 공유 컴파일러 파일은 작업 소유권을 조정해 충돌을 피한다. P2는 공통 의미/타깃 경계가 확보되는 대로 시작할 수 있다. **M1 부팅 게이트 완료**. 다음 언어 게이트는 **M2**이고, Linux 사용자 프로그램 타깃은 별도의 미완료 트랙이다.

## AI 에이전트의 완료 보고 규칙

- 비전공자도 시연할 수 있는 방법 → 실제 수행한 명령과 결과 → 통과·실패 테스트 → 아직 **NOT RUN**인 증거 → 남은 위험과 다음 작업을 명확히 설명한다.
- 결과물을 직접 체험하는 것이 중요한 목표지만, **실행한 적 없는 이미지나 문서만으로 성공 표시 금지**. 위험한 배포/파괴적 변경은 추가 승인 필요.
- 개발 중 새 근거가 나오면 우선순위를 조정하되 [INTERVIEW_DECISIONS.md](INTERVIEW_DECISIONS.md)의 사용자 답변과 에이전트의 기술 판단을 혼동하지 않는다.
